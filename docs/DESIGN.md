# 思路与取舍：先把电视当作自己的屏幕

起点很简单：已有HA、已有电视App，缺的是一个干净、可退出的入口。我们不想造内容平台，也不想把HDMI接入的Mac/Apple TV控制逻辑混进电视桌面。Android App只运行在电视上，电视系统处理音量、输入源和电源；Mac音量键控制是另一个项目。

## 页面结构

- 家庭页：承载原来的HA网页，给它尽可能大的区域；不重新映射实体，不维护第二套家庭状态。
- App资源库：找到系统允许查询的可启动App，直接打开。自研App也是普通入口。
- 网页入口：服务书签，不是服务聚合后台。当前只有一个可编辑外部网页书签。
- 时钟/背景：属于桌面的基础能力。原生实现先给内置背景；文件选择、闲置画面、缩放等在设计稿探索。
- 设置与恢复：把原桌面/系统设置入口留在手边，诊断和恢复属于具体场景，不持续堆满首页。

视觉借鉴Apple TV清楚的焦点、大屏留白与内容层级，避免复制品牌或暗示官方关联。自然海岸/暖灰基底、明确的浅蓝焦点，不用绿色或紫色主题；遥控器可读性比堆玻璃效果更重要。当前原生页面是能力验证壳，设计稿才是完整体验探索；两者不能混为完成度。

## 为什么保留原HA页面

用户已经维护了一套HA布局，不应为了电视再抄一份。WebView是嵌入网页的控件，不是完整浏览器：我们要补返回和刷新，但不把凭据转移到自建后台。代价是旧内核、自定义卡片、SSO以及遥控焦点兼容性要真正测；“网页能打开”不等于“所有按钮都能遥控”。

## 为什么暂不接管HOME

先用普通App证明安装、退出、网页、遥控和恢复。修改默认HOME、开机抢前台或禁用原桌面会把“UI错误”变成“系统入口丢失”。当前没有这些能力。未来如真有必要，须先做厂商/固件兼容研究、独立回退路径和人工验收，而不是加一条shell命令就发布。

## Agent怎样接入：选择还在探索

| 路线 | 适合什么 | 代价与现状 |
| --- | --- | --- |
| ADB + 本机脚本 / scrcpy | 开发、安装、观察、明确授权的按键 | 能力很大；UI布局可能不完整，焦点/时序脆弱。用于测试，不能称最小权限产品API |
| HA Android TV Remote | 支持该服务的电视上发遥控/启动App | 需要电视有Android TV Remote Service，不等于读懂任意页面；没有保证所有国行固件支持 |
| 本App动作接口 | 将来明确的“打开应用/进入家庭页/退出”等动作 | **尚未实现**。应先做动作白名单、会话认证、本地绑定、过期撤销、限流/审计，拒绝任意shell和自动家电动作 |
| 无障碍/读屏Agent | 某些第三方方案探索UI树和动作 | 权限与隐私成本高、并非TV通用适配；当前不要求、不集成，不因安装指南就授予 |

未来扩展优先小而明确的动作，而不是公开整机shell。远程控制必须让用户知道谁在控制、可以撤销、不会误操作HA；VPN只解决网络可达性，不等于身份认证和操作授权。当前的“扩展与Agent”按钮只显示说明，不能当成已支持插件。

可参考的真实项目：[Android ADB](https://developer.android.com/tools/adb)、[scrcpy](https://github.com/Genymobile/scrcpy)、[HA Android TV Remote](https://www.home-assistant.io/integrations/androidtv_remote/)、[Mobile MCP](https://github.com/mobile-next/mobile-mcp)。这些是独立项目，未捆绑、未审计其所有行为，手机演示不等于电视兼容；不要为了试它们默认装新的整机控制服务。

## 接下来值得做的事

先收集逐机兼容反馈，修焦点/返回与网页失败恢复；再把完整设计稿逐步落实。优先记录真实问题而非扩成海报墙、播放历史或跨App内容抓取。默认桌面切换、任意壁纸导入、完整全屏壳、Agent API和用户配置导出是待评估工作，不是现在的承诺。
